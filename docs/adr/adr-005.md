# ADR-005 : Organisation du code (couches / structure)

- Statut : Accepté
- Date : 2026-11-03

## Contexte
Sans séparation des responsabilités, un projet web devient vite illisible et
non testable. VetTime doit rester lisible pour le prof (entretien) et testable
en CI (pytest). Il fallait trancher une structure de modules.

## Décision
Architecture en couches, une responsabilité par module :
- `app/main.py` — point d'entrée FastAPI + endpoints (routes) ; montage de l'app.
- `app/models.py` (SQLAlchemy 2.0, 151 lignes, 11 tables) — modèles ORM =
  source de vérité vs `docs/schema-v1.sql`.
- `app/database.py` — moteur PostgreSQL + engine / SessionLocal / Base.
- `templates/` (Jinja2 + HTMX) — rendu server-side (Jalon 3).
- `tests/` — `test_models.py` (11 tables), `test_health.py`, `test_health_db.py`
  (DB connectée), `test_app.py` — tous verts en CI.
- `docs/` — ADRs, schéma, blogues, transparence IA.
- Les règles métier (paie, banques, verrouillage) vivent dans des fonctions /
  services, pas dans les routes.

## Alternatives considérées
- **Fichier unique `app.py`** (tout en un) : rapide au départ, mais illisible et
  non testable à mesure que le MVP grandit. Rejeté.
- **Package `routers/` par domaine dès maintenant** : propre, mais surkill pour
  le nombre actuel d'endpoints ; refactor possible au Jalon 3. Gardé en réserve.
- **DDD / services lourds** : surkill pour un MVP de cours. Rejeté.

## Conséquences
- `models.py` ↔ `schema-v1.sql` doivent rester en miroir (11 tables).
- Tests isolés (pytest) valident la couche modèles + santé DB en CI.
- Le prof peut naviguer le code lors de l'entretien (couches explicites).
