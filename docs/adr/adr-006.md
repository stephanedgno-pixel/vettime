# ADR-006 : Banques de congés — modèle ledger (journal des mouvements)

- Statut : Proposé
- Date : 2026-11-27

## Contexte

Règles de paie validées cliente (schéma v1.1, règles #4/#5/#6) :
- **#4** Banque vacances : au renouvellement (~1er mai), solde **reporté** (carry-over).
- **#5** Banque maladie : au renouvellement (~1er janvier), solde **payé** si inutilisé (cash-out), sinon perdu.
- **#6** Correction post-verrou : reportée à la paie suivante ; modif/discrepance **approuvée par admin OU gérant** (jamais par l'employé seul).

Critique explicite du prof (retour Jalon 2) : *« les banques de congés ne gardent ni historique ni mouvements »*.

**État démontrable dans le dépôt** (`docs/schema-v1.sql` v1.1) :
- `banques_vacances` et `banques_maladie` ne possèdent que `solde_actuel` (DECIMAL),
  `renouvellement` (DATE), `annee`. **Aucune table de mouvements, aucune colonne d'historique.**
- `demandes_conge` porte `statut` + `approuve_par`/`approuve_le`, mais **aucune clé étrangère
  ne lie une demande approuvée à une variation de banque**. Rien n'enregistre qu'une
  approbation a décrémenté un solde.

→ Le solde est une valeur « écrasée » sans trace. On ne peut ni prouver ni reconstruire
son évolution. C'est exactement la critique du prof, et le schéma le prouve.

## Décision

Adopter un **modèle ledger** : toute variation de banque est un enregistrement dans une
nouvelle table `mouvements_banque`. Le solde devient la somme des mouvements
(source unique de vérité), avec un `solde_apres` dénormalisé pour une lecture O(1) et une piste d'audit.

Les tables `banques_vacances` / `banques_maladie` sont conservées pour les métadonnées
(renouvellement, année) et comme cache du solde courant (`solde_actuel` = dernier
`solde_apres`), sous l'invariant `solde_actuel == SUM(montant)`.

## Types de mouvements (CHECK)

- `accumulation` : crédit de vacances/maladie (acquisition périodique).
- `utilisation` : prise de congé (débit), liée à `demandes_conge`.
- `ajustement` : correction manuelle (règle #6), par admin/gérant, avec motif.
- `cash_out` : paiement du solde maladie inutilisé au renouvellement (règle #5).
- `renouvellement` : report du solde vacances au renouvellement (règle #4).
- `initial` : amorçage (migration) — un seul par employé/banque.

## Avantages

1. **Auditabilité** : chaque mouvement porte `cree_par` (qui), `date_mouvement` (quand),
   `note` (pourquoi). Répond directement à « ni historique ni mouvements ».
2. **Reconstruction du solde** : `SELECT SUM(montant) ...` ou lecture du dernier
   `solde_apres`. Source unique de vérité.
3. **Historique des corrections** : un `ajustement` s'ajoute, il n'écrase pas
   (règle #6 traçable, approuvée par admin/gérant).
4. **Cash-out maladie modélisé** (règle #5) : mouvement `cash_out` explicite, pas un effacement.
5. **Renouvellement modélisé** (règle #4) : mouvement `renouvellement` explicite (carry-over).

## Désavantages / risques

1. **Complexité** : tout changement de solde doit insérer un mouvement (pas d'écriture
   directe de `solde_actuel`). Nécessite un helper d'écriture unique.
2. **Migration** : `solde_actuel` existant doit être amorcé par un mouvement `initial`
   (un par employé/banque) pour que `SUM(montant)` corresponde. Étape obligatoire.
3. **Requêtes supplémentaires** : la lecture du solde passe par le dernier `solde_apres`
   (indexé) — coût négligeable ; sinon SUM sur peu de lignes.
4. **Cohérence** : l'invariant `solde_actuel == SUM(montant)` doit être gardé par un test,
   sinon dérive silencieuse.

## Comparaison explicite

| Aspect | Actuel (`solde_actuel` seul) | Proposé (ledger) |
|---|---|---|
| Historique des changements | Aucun | Chaque mouvement tracé (date / auteur / motif) |
| Mouvements | Aucun | 6 types (accumulation, utilisation, ajustement, cash_out, renouvellement, initial) |
| Lien demande → banque | Aucun (pas de FK) | `id_demande` sur `utilisation` |
| Reconstruction du solde | Colonne directe | `SUM(montant)` ou dernier `solde_apres` |
| Correction (règle #6) | Écrasement du solde | Mouvement `ajustement` tracé, approuvé |
| Cash-out maladie (règle #5) | Non modélisé | Mouvement `cash_out` |
| Renouvellement (règle #4) | Non modélisé | Mouvement `renouvellement` |
| Complexité | Minimale | +1 table + helper d'écriture + test d'invariant |
| Migration | — | Amorçage `initial` requis |

## Schéma proposé (DDL — v1.2, à valider)

```sql
-- Journal des mouvements de banques (vacances + maladie)
CREATE TABLE mouvements_banque (
    id_mouvement     SERIAL PRIMARY KEY,
    id_employe       INT NOT NULL REFERENCES employes(id_employe),
    type_banque      VARCHAR(10) NOT NULL CHECK (type_banque IN ('vacances','maladie')),
    type_mouvement   VARCHAR(15) NOT NULL CHECK (type_mouvement IN
        ('accumulation','utilisation','ajustement','cash_out','renouvellement','initial')),
    montant          DECIMAL(6,2) NOT NULL,  -- delta signé : + crédit, - débit
    solde_apres      DECIMAL(6,2) NOT NULL,  -- solde après ce mouvement (audit + lecture O(1))
    date_mouvement   TIMESTAMP NOT NULL DEFAULT NOW(),
    id_demande       INT REFERENCES demandes_conge(id_demande),  -- NULL sauf 'utilisation'
    cree_par         INT REFERENCES utilisateurs(id_utilisateur), -- qui a enregistré (règle #6)
    note             VARCHAR(200),           -- motif / raison (correction, cash-out, ...)
    UNIQUE(id_employe, type_banque, date_mouvement, type_mouvement)
);
CREATE INDEX idx_mouv_employe_banque ON mouvements_banque(id_employe, type_banque, date_mouvement);

-- Invariant à faire respecter (test) :
--   banques_vacances.solde_actuel == SUM(montant) WHERE type_banque='vacances' AND id_employe=?
--   banques_maladie.solde_actuel  == SUM(montant) WHERE type_banque='maladie'  AND id_employe=?
```

**Migration** (à faire en même temps que l'implémentation, pas maintenant) : pour chaque
`(employe, banque)` existant, insérer un mouvement `initial` avec `montant = solde_actuel`,
`solde_apres = solde_actuel`. Aucun code applicatif n'est modifié par cette proposition
(schéma seulement).

## Détails de conception

### Justification de `solde_apres` (dénornalisation du solde courant)

`SUM(montant)` reconstruit le solde de façon autoritaire, mais `solde_apres` est
conservé comme **snapshot dénormalisé** pour trois raisons distinctes :

1. **Performance des lectures (O(1) vs O(n))** : `SUM(montant)` parcourt toutes les
   lignes de l'employé (potentiellement des dizaines à centaines sur une année,
   corrections comprises). Pour un rapport de paie qui itère sur **tous les employés**
   à la fermeture de période, cela fait N parcours complets. Lire la dernière ligne
   (`solde_apres`, indexée sur `(id_employe, type_banque, date_mouvement)`) donne le
   solde courant en O(1) — comme le solde courant d'un compte bancaire, qu'on ne
   recalcule pas depuis l'ouverture à chaque affichage.
2. **Audit / intégrité (détection de corruption)** : `solde_apres` rend chaque ligne
   **auto-vérifiable** : `solde_apres(N) == solde_apres(N-1) + montant(N)`. Toute ligne
   supprimée, montant altéré ou insertion fantôme **casse la chaîne** et devient
   détectable (test d'invariant). Avec seulement `SUM(montant)`, une ligne corrompue
   passe inaperçue (le total reconstruit est faux mais cohérent). C'est le mécanisme
   standard des relevés bancaires (solde courant affiché à chaque ligne pour cette
   raison précise).
3. **Rapports / solde à une date précise** : `solde_apres` permet de lire le solde
   *au 30 avril* en prenant la dernière ligne `date_mouvement <= '2026-04-30'`, sans
   agréger. (Combine avec `SUM(... WHERE date <= X)` — redondant mais peu coûteux.)

`SUM(montant)` reste la **source de vérité** (reconstruction + vérification) ;
`solde_apres` est le **chemin rapide + piste d'audit par ligne**. Ils sont
complémentaires, liés par l'invariant `solde_actuel == SUM(montant)` (test requis).
Trade-off assumé : un peu plus de complexité d'écriture (le writer calcule
`solde_apres`) et de stockage, pour un gain de perf/audit. Si le volume de mouvements
était minuscule, `SUM` seul suffixait ; le bénéfice croît avec le volume et les rapports
(2e critique du prof : « écarts horaire/réel reportés » → besoin de rapports).

### Clarification du mouvement `renouvellement`

Rappel règles clientes : #4 banque **vacances** ~1er mai = solde **reporté** ;
#5 banque **maladie** ~1er janvier = solde **payé si inutilisé** (cash-out), sinon perdu.

**Banque vacances — carry-over (règle #4), exemple concret :**
- 30 avr : dernière ligne avant renouvellement, `solde_apres = 40.00`.
- 1er mai (`renouvellement`) : `montant = 0.00`, `solde_apres = 40.00`,
  `note = "Renouvellement 2026-2027, report du solde (règle #4)"`. Le champ `annee`
  de `banques_vacances` bascule à 2026-2027.
- 15 mai (`utilisation`) : `montant = -8.00`, `solde_apres = 32.00`.

Le `montant = 0` : le solde ne change pas (il est reporté). **Pourquoi cette ligne
existe-t-elle malgré un delta nul ?** Parce que c'est un **événement métier réel**
(ouverture de la nouvelle année d'acquisition, report légal du solde) et qu'elle
**rend le ledger continu à travers les années** : sans elle, la transition
40 → 32 traverserait la frontière du 1er mai sans qu'aucune ligne n'en explique le
report. Elle ancre aussi `renouvellement`/`annee`. Les ledgers financiers incluent
systématiquement des lignes à delta nul (« solde reporté », « période close ») pour
une piste d'audit complète — exactement ce que visait la critique du prof
(« ni historique ni mouvements »).

**Banque maladie — cash-out (règle #5), exemple concret :**
- 31 déc : `solde_apres = 12.50`.
- 1er janv (`renouvellement`) : si `solde_actuel > 0` → mouvement **`cash_out`**,
  `montant = -12.50`, `solde_apres = 0.00`, `note = "Cash-out solde maladie
  inutilisé (règle #5)"`. La banque repasse à 0 ; `annee` → nouvelle année.
- Si `solde_actuel` était déjà 0 (tout consommé) : **aucun `cash_out`** (rien à payer),
  pas de ligne delta-nul nécessaire (le solde est déjà 0).

→ Pour la maladie, l'effet de valeur du renouvellement est le `cash_out` (règle #5) ;
pas de ligne delta-nul (la banque se réinitialise simplement à 0). Pour les vacances,
le renouvellement est la ligne `renouvellement` à delta 0 (carry-over).

**Renouvellement = mouvement dans le ledger, ou événement métier séparé ?**
- **Approche A (retenue) — renouvellement = mouvement du ledger** (delta 0 vacances,
  `cash_out` maladie) : une seule table, piste continue et auto-auditable, lectures
  simples. Coût : lignes à delta nul (bruit mineur, standard en comptabilité).
- **Approche B — renouvellement = entité événement séparée** (`evenements_banque` ou
  table `renouvellements`), carry-over implicite (continuité du ledger, sans ligne
  delta 0) : séparation sémantique plus nette (événements vs variations de valeur),
  mais la reconstruction « qu'est-il arrivé au renouvellement ? » exige une jointure
  événement + ledger, et le report n'est prouvé par aucune ligne.
- **Choix A** : elle répond au plus près à la critique du prof (manque d'historique /
  mouvements) en privilégiant l'explicitation dans le ledger. Le delta-nul est justifié
  comme marqueur d'événement métier.

**Solde après** : vacances = 0.00, maladie = 0.00

| 6 | maladie | accumulation | +5.00 | 5.00 | 2026-11-01 | — | 1 | Accumulement maladie automne |

### Vérification de l'invariant
- vacances : 0 + 10 - 4 + 2 = 8.00 = dernier `solde_apres` ✓
- maladie : 0 + 5 - 5 = 0.00 = dernier `solde_apres` ✓

## Alternatives considérées

- **Garder `solde_actuel` + ajouter une table d'audit en lecture seule** : n'empêche pas
  l'écriture directe du solde (dérive possible). Rejeté au profit du ledger comme source unique.
- **Une table de ledger par banque** (`mouvements_vacances` / `mouvements_maladie`) : dupplique
  la structure. Rejeté au profit d'une seule table discriminée par `type_banque` (cohérent avec
  `demandes_conge.type_conge`).

## Conséquences

- Répond directement à la critique du prof (historique + mouvements démontrables dans le schéma).
- Modélise explicitement les règles #4/#5/#6 (renouvellement, cash-out, ajustement approuvé).
- Ajoute une table + une discipline d'écriture unique + un test d'invariant.
- **Aucune nouvelle fonctionnalité UI** pour l'instant (conforme à la consigne « pas de feature maintenant »).
- Implémentation (SQLAlchemy, migration, helper d'écriture, routes d'approbation) différée
  jusqu'à validation de cette ADR.
